			EUC-JP から Unicode へ

			残りをどうするか


1. どこまで済んだか

実行時に意味を持たない 212 ファイルを UTF-8 にした。文書 (fml/doc/ja)、
モジュールに付いた日本語のコメント、道具の類である。これらは読まれる
だけで、符号を変えても fml8 の振る舞いは変わらない。

残っているのは 207 ファイルで、内訳は三つに分かれる。

	159	fml/share/message/euc-jp/	メールで送られる定型文
	 40	fml/etc/			設定と設定テンプレート
	  5	テスト材料			オクテット列そのものが対象
	  3	fml/lib の言語処理		日本語がコード中にある

t/95_encoding.t が、この四つの理由のどれにも当たらない EUC-JP が
現れたら落ちる。移行が「やり残し」ではなく「そこは残すと決めた」で
あることを、機械が見張る形にしてある。


2. なぜ残りが難しいのか

2.1 fml/share/message/euc-jp/

ディレクトリ名が符号そのものである。$template_file_charset_ja が
euc-jp で、そこから

	$fml_share_dir/message/$template_file_charset/...

という道が組み立てられる。UTF-8 にするには

	・fml/share/message/utf-8/ を作る
	・$template_file_charset_ja を utf-8 にする
	・送信時にどの符号でメールに載せるかを決める

の三つが要る。三つ目が本体である。いまは定型文の符号がそのまま
メールの符号になるが、日本語のメールは長く ISO-2022-JP で送られてきた。
定型文を UTF-8 にしたうえで ISO-2022-JP に変換して送るのか、
UTF-8 のまま送るのかは、受け取る人の環境の話であって符号変換の話では
ない。

なお issue #8 の調査で分かったことがある。この道は現在も壊れていて、
ヒント分岐が language_to_message_charset() を呼ぶために iso-2022-jp と
いう名前のディレクトリを探しており、そんなディレクトリは存在しない。
つまり日本語の定型文は一度も読まれていない。fix-issue-8 がそれを直す。
share/message を動かす前に、そちらが先である。

2.2 fml/etc/

config.cf と default_config.cf。設定ファイル自身の符号と、そこに
書かれている $template_file_charset のような値は別の話である。
前者だけ UTF-8 にすることはできるが、fml8 は config.cf を読むときに
符号を宣言していないので、日本語のコメントを含む行をどう読むかが
決まっていない。

FML::Config が読み込み時に decode するようにしてから動かすのが順序。

2.3 fml/lib の言語処理 3 ファイル

これがいちばん厄介である。

	Mail/Message/Language/Japanese/Subject.pm
	Mail/Bounce/Language/Japanese.pm
	FML/Demo/Language/Japanese.pm

Subject.pm を見ると分かる。

	$pattern .= '|(返信|返|ＲＥ|Ｒｅ)(\s*:|：)';
	...
	&Jcode::convert(\$x, 'euc');
	return ($x =~ /^((\s|(　))*($pattern)\s*)+/ ? 1 : 0);

Subject を euc に変換してから、EUC-JP のオクテット列として書かれた
パターンで照合している。ソースを UTF-8 にすると、パターンのバイト列が
変わるのに変換先は euc のままなので、日本語の Re: 検出が黙って壊れる。
全角空白 (　) も同じである。

正しい直し方は符号変換ではない。Subject を「文字列」として扱うこと、
つまり decode してから照合し、パターンも文字として書くことである。
それは Encode への移行そのもので、fix-charset-and-bugs の仕事と重なる。


3. 順序

	1. fix-issue-8		テンプレート探索の道を直す。いま日本語の
				定型文は読まれていない
	2. Encode 移行		Jcode / Unicode::Japanese をやめ、
				メールを文字列として扱う。言語処理 3 ファイルは
				これで直る
	3. fml/etc		FML::Config が decode するようにしてから
				設定ファイルを UTF-8 に
	4. fml/share/message	utf-8/ を作り、送信時の符号を決める

2 が終わるまで 4 に手を付けない。定型文の符号を変えても、それを
どう送るかが決まっていなければ意味が無い。


4. 安全網

fml4-parity が Subject tag の扱いを fml4 と突き合わせている。

	t/28_parity_subject_tag.t
	t/31_behaviour_subject_tag.t

Re: の検出と subject tag の付け方が変わったらここが落ちる。言語処理を
触るときはこれを見ながら進める。

t/95_encoding.t は符号そのものを見る。理由の無い EUC-JP、置換文字の
混入、コード中に日本語を持つモジュールの一覧、の三つ。


5. リリースとの関係

非互換を入れられるのはリリース前だけである。fml8 は v7.99.1 という
tag があるだけで、8.0 は出ていない。定型文の符号や設定ファイルの
符号を変えるのは、既に運用している人の手元を変える種類の変更なので、
やるならこの区切りしかない。

逆に言えば、この四段を終えてからリリースする、という順番になる。
